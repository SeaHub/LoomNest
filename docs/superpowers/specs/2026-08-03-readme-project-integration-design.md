# LoomNest README 项目接入文档设计

## 目标

将仓库根目录的 `README.md` 重写为中文操作手册，使维护者和未来的 AI 都能仅依据该文档，将一个已经独立部署的外部项目添加到 LoomNest 的作品列表中。

“接入”只表示在 LoomNest 登记项目的展示信息、宣传素材和访问入口。外部项目继续独立开发与部署；不得将其源码、依赖或构建产物复制到 LoomNest，也不得让 LoomNest 负责构建外部项目。

## 文档形式

采用单 README、执行手册式结构。项目简介、开发命令、配置契约、接入步骤、验证方式和故障排查全部集中在根目录 `README.md`，避免 AI 因跨文件检索而漏掉关键约束。

README 使用中文，命令、文件路径、字段名和配置值保留原始英文。步骤使用明确的编号、输入条件、操作、检查点和完成标准，避免依赖隐含上下文。

## 内容结构

README 按以下顺序组织：

1. 项目定位：说明 LoomNest 是外部数字作品的展示索引，而不是多项目构建平台。
2. 快速开始：列出安装、开发、测试、构建和生产预览命令。
3. 目录与权威配置源：明确正式站点只读取 `public/works.json` 和 `public/assets/`；`prototype/` 仅供视觉参考。
4. 标准接入流程：从确认项目类型、准备素材、编辑 JSON、本地验证到发布，形成可顺序执行的检查清单。
5. 配置契约：解释作品对象的全部字段、允许值、默认行为和路径约束。
6. 分类型示例：分别提供 `web`、`mini-program`、`mobile` 和 `future` 的可复制 JSON 示例。
7. AI 执行规则：约束修改范围、要求读取现有配置、保持 JSON 有效、避免覆盖其他作品，并规定必须运行的验证命令。
8. 故障排查：覆盖配置加载失败、链接不显示、图片不显示、筛选分类不正确和部署路径问题。
9. 发布说明：说明推送到 `main` 后由 GitHub Actions 自动测试、构建和发布。

## 配置契约

README 必须基于当前实现描述以下事实：

- 正式作品列表是 `public/works.json` 顶层 JSON 数组，数组顺序就是页面展示顺序。
- 每项使用唯一、稳定的 `id`；建议使用小写英文、数字和连字符。
- `type` 的受支持值为 `web`、`mini-program`、`mobile`、`future`。
- `status` 使用 `live` 或 `soon`。当 `status` 为 `soon` 或 `type` 为 `future` 时，页面展示 `Coming Soon`，忽略访问链接。
- `web` 使用 `access.url`；`mini-program` 使用 `access.qrImage` 和可选的 `access.qrAlt`；`mobile` 使用 `access.appStore` 和/或 `access.googlePlay`；`future` 使用空的 `access` 对象。
- 外部链接只有 `http://` 或 `https://` 协议会被渲染。缺失或不安全的链接不会成为可点击入口。
- 宣传图和二维码放入 `public/assets/`，在 JSON 中使用以 `./assets/` 开头的相对路径。
- 当前自动测试要求每个作品的 `image` 存在，且扩展名为 `.jpg`、`.jpeg` 或 `.webp`；二维码可以使用 `.png`。
- 缺失字段会由页面标准化逻辑补默认值，但接入流程应要求显式填写核心展示字段，不能依赖默认值发布内容。
- `public/works.json` 无法加载、JSON 无效或数组为空时，页面会显示提示并回退到 `src/App.vue` 内置示例；这是容错行为，不代表接入成功。

## 标准接入流程

README 的流程需要让执行者完成以下动作：

1. 对 `live` 项目确认其已经独立部署，并准备最终访问 URL；`future` 或 `soon` 项目不要求 URL。
2. 根据用户实际访问方式选择唯一的 `type`，不要通过新增任意类型扩展现有 UI。
3. 准备压缩后的宣传图；小程序额外准备可扫描二维码及准确替代文本。
4. 使用不冲突的文件名将素材放入 `public/assets/`。
5. 读取现有 `public/works.json`，在目标位置新增一个对象，不删除或改写无关项目。
6. 按项目类型填写对应的 `access` 字段，并删除不适用的入口字段。
7. 检查 JSON 语法、`id` 唯一性、素材路径和 URL。
8. 运行 `npm test` 和 `npm run build`。
9. 使用 `npm run dev` 或 `npm run preview` 人工检查筛选、展开详情、图片和访问入口。
10. 提交修改；推送 `main` 后等待 GitHub Pages 工作流完成。

## AI 执行规则与完成标准

README 要包含面向 AI 的显式规范：

- 修改前先读取 `README.md`、`public/works.json` 和目标素材目录。
- 若项目类型、正式 URL、标题、年份或素材缺失，不得捏造；应向用户索取缺失信息，或按用户明确要求使用 `future` 状态。
- 只修改本次接入所需的配置和素材，不编辑 `dist/`、`node_modules/` 或 `prototype/works.json`。
- 保留现有 JSON 数组及无关记录，避免格式化整个仓库或进行无关重构。
- 不把示例域名、应用商店首页或无法扫描的占位二维码当作正式完成结果。
- 必须报告新增或修改的记录、素材路径，以及测试和构建结果。

接入完成需同时满足：JSON 可解析；`id` 唯一；素材存在；入口符合类型；`npm test` 和 `npm run build` 通过；本地页面能在正确分类显示项目并呈现可用入口。

## 异常与排查

故障排查应把页面表现映射到可执行检查：

- 页面提示正在使用示例数据：检查 `public/works.json` 是否为非空数组、JSON 是否有效，以及开发服务器请求路径。
- 图片不显示或测试失败：检查大小写、文件扩展名、文件是否位于 `public/assets/`、配置路径是否以 `./assets/` 开头。
- 链接不显示：检查类型对应的 `access` 键以及 URL 是否使用 HTTP(S)。
- 项目出现在错误筛选中：检查 `type` 是否为四种受支持值之一。
- 页面顺序不正确：调整 `public/works.json` 中对象的数组顺序，而不是修改组件代码。
- GitHub Pages 正常构建但资源丢失：保持配置使用相对资源路径，不要写站点根路径 `/assets/...`。

## 验收与范围

本次只重写 `README.md`，不改变页面逻辑、配置格式、测试脚本、素材或部署流程。最终文档必须与当前实现一致，示例 JSON 可直接复制后修改，并让不了解仓库历史的 AI 能在不读取设计文档的情况下独立完成一次项目接入。
